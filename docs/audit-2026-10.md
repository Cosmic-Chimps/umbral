# Documentation audit, October 2026

Audited on 2026-10-23 at `76531b2` (release 0.4.0, the tip of `main`) by the
documentation reviewer session (`umbral-documentation`). The code is normative
and the constitution (3.0.0, Principle VI) is the bar: each connector ships a
walkthrough; every operator-facing error says what to do next; the README gets
a reader from zero to a working login without leaving the page.

What was read: README.md (1314 lines), `docs/connectors/*` (5),
`docs/secret-stores/*` (4), `docs/vision.md`, PRODUCT.md, DESIGN.md,
CHANGELOG.md, and the code each of them describes: `Program.fs`,
`Infrastructure/` (PublicOrigin, TrustedProxies, DataDirectory, Keys, Database,
UserStore, Linking, AppClients, SecretMove, the secret stores and their
Registry, WebAuthn, Passkeys), `Handlers/` (Admin, Connect, Passkeys, Health),
`Views/Texts.fs` and `Views/Layout.fs`, the Dockerfile, the compose file,
`.dockerignore` and the CI workflows. Every finding names the doc line and the
code it was checked against. Nothing was changed during the audit.

How to read this file: sections 1 to 4 are the findings, numbered so a task can
cite them. Section 5 turns them into tasks in the order to run them, each with
acceptance criteria. Section 6 is the review process for documentation changes
from here on.

## Verdict

The documentation is in good shape where it matters most. Every setting in the
reference exists with the documented default; every UI label the README quotes
is in `Texts.fs` verbatim; the troubleshooting entries match the code paths;
the callback paths, scopes and claim mappings in the connector walkthroughs
match the adapters; the backup and reset commands match the Dockerfile. Of
about 150 failure messages, 8 operator-facing ones have no next action and 9
have a partial one.

What needs fixing, in order of harm:

1. **Statements that contradict the code** (section 1). The worst are in
   "Integrate an app": a claim (`preferred_username`) the code never emits, and
   two rules about email and linking an app developer would code against and
   get wrong. The OpenID Connect walkthrough still documents the YAML
   configuration file that spec 004 removed and an Extra scopes field that is
   not in the form. All four store walkthroughs say a refused credential is
   ridden out by the cache; only an unreachable store is.
2. **Gaps in the zero-to-login path** (section 2, M1 to M3): the quick start
   never tells the reader to click **Create app**, and its first command has a
   placeholder URL.
3. **Error messages without a next action** (section 3), including UI strings
   that point at a `docs/` path that is not in the image and at a container
   name compose does not use.
4. **Length** (section 4): the README is 1314 lines because it also hosts a
   253-line Caravana deployment guide. Move it, and the README is a README
   again.

## 1. Wrong or out of date

Each item: where, what the doc says, what the code does.

### README

- **W1. `preferred_username` is promised and never emitted.** README:336: "`name`,
  `preferred_username`, `picture` come with the `profile` scope when the
  provider supplied them". The claim is registered
  (`Infrastructure/OpenIddictSetup.fs:309`) and has a destination
  (`Handlers/Connect/Authorize.fs:55`), but neither `setProfileClaims`
  (`Authorize.fs:96-118`) nor the userinfo handler
  (`Handlers/Connect/UserInfo.fs:42-63`) sets it. In the same sentence, `name`
  is never absent: `Infrastructure/UserStore.fs:131` falls back to "GitHub
  user", "Discord user" and so on, and a passkey user's name is the one they
  typed.
- **W2. An unverified email is not missing; it is emitted as unverified.**
  README:333-335: "`email` and `email_verified` may be missing. A GitHub user
  can keep their email private, a Discord account can be unverified, and a
  passkey-only user has none. Handle all three." The code emits `email` with
  `email_verified: false` in the Discord case (`UserStore.fs:123-136`,
  `UserInfo.fs:56-62`); both claims are absent only when the user has no email
  at all. An app written to the README treats an unverified address as absent,
  or misses that the flag can be `false`.
- **W3. The OIDC identity rule reads as "no linking by email".** README:400-403:
  "For an OpenID Connect provider you added, a person is identified by that
  provider's issuer address together with their id there, so two providers
  never merge people". Linking by a verified email applies to every connector
  kind, OIDC included (`Domains/Linking.fs`, `UserStore.fs:96-100`), and the
  connector form's own warning says so (`Texts.fs`,
  `ConnectorEmailTrustWarning`). What is true: the provider-account key is
  `issuer#sub` (`Domains/Connectors.fs:329`), so two issuers are never the same
  *account*. The OIDC walkthrough ("What Umbral takes from your provider") says
  it right; the README should match it.
- **W4. Passkeys break on a host change, not on any origin change.**
  README:683-685 and `docs/connectors/passkey.md:21-23`: "A passkey belongs to
  the address in `UMBRAL__PUBLIC_ORIGIN`. If you change it, every passkey stops
  working." The relying-party ID is the host only
  (`Infrastructure/WebAuthn.fs:101-104`, `RPID = origin.Uri.Host`); a change of
  scheme or port keeps them. Say "the host name in `UMBRAL__PUBLIC_ORIGIN`".
- **W5. Three screens or four.** README:167 says the admin area has three
  screens; README:415 and PRODUCT.md:103 say the side rail has four. The rail
  has four entries (`Views/Layout.fs:51-55`: Apps, Connectors, Users,
  Credential). The constitution counts three top-level screens; Credential is a
  page about the operator, not a concept. One wording everywhere: "three
  screens, Apps, Connectors and Users, and the Credential page".
- **W6. "Credential in the top bar"** (README:159). It is in the side rail
  (`Layout.fs:55`), as README:415 says.
- **W7. The schema-upgrade warning is written twice.** README:535-548: one
  paragraph for schema version 4 (branding), then the same paragraph for
  version 6 (passkeys). `Database.fs:246` has `SchemaVersion = 6`. Keep one
  paragraph, version 6, in "Your data: back it up" where upgrades belong; the
  branding section points at it.
- **W8. `move-secrets` output.** README:1169-1172 lists the per-connector words
  as `moved`, `skipped`, `failed`, `warning`. A dry run prints `would move`
  (`Texts.fs:1052`); a connector edited mid-move prints "changed while it was
  being moved, so nothing was overwritten; run the command again"
  (`Texts.fs:1053`), not the `being edited` text the README quotes; the summary
  line is "N connectors: X moved, Y already in place, Z changed meanwhile (run
  it again), W failed" (`Texts.fs:571-575`); and a `warning` (the old copy could
  not be deleted) leaves the exit code 0 (`Infrastructure/SecretMove.fs`,
  `MoveLeftBehind`), which README:1167 does not say.
- **W9. The proxy's `Host` handling does matter.** README:774-775: "Every URL Umbral
  publishes comes from `UMBRAL__PUBLIC_ORIGIN`, never from the `Host` header,
  so the proxy's host handling does not matter." True for published URLs,
  false for the origin-mismatch banner, which compares the forwarded scheme
  and host with the configured origin (`Handlers/Admin/Connectors.fs:37-49`,
  after `UseForwardedHeaders`, which reads `X-Forwarded-Host`,
  `TrustedProxies.fs`). nginx rewrites `Host` to the upstream name by default,
  so an operator who follows README:776-778 gets a false banner on Connectors.
  Add `proxy_set_header Host $host;` to the nginx lines, and say which header
  the banner reads.
- **W10. "This server only accepts HTTPS requests." is not Umbral's.**
  README:764 and :1255 say Umbral answers with it. It is OpenIddict's text,
  shown only on the OIDC endpoints (`/connect/*`) through
  `Handlers/Connect/Error.fs`, under the heading "That sign-in request was
  rejected"; `/admin` and `/` never show it. Say where it appears.
- **W11. The settings table understates the insecure pair and "localhost".**
  README:1186: `ASPNETCORE_ENVIRONMENT=Development` plus
  `UMBRAL__INSECURE_ALLOW_HTTP=true` "allow plain `http://localhost`". The pair
  is matched case-sensitively (`Program.fs:202-204`) and does more: it removes
  OpenIddict's HTTPS requirement on every host (`OpenIddictSetup.fs:358-359`)
  and lets a loopback `http://` issuer through when adding an OIDC connector
  (`Infrastructure/OidcDiscovery.fs:74-79`). And `http://localhost` itself
  needs no flag: `PublicOrigin.fs:77-83,110` accepts `localhost`, `127.0.0.1`,
  `::1` and `[::1]` on plain http, and the flag opens the sign-in endpoints.
  The quick start's "which Umbral allows only when you ask" (README:86, 124) is
  right in effect and wrong in reason. README:70 and :1183 should say
  "`localhost` or a loopback address".
- **W12. The backup table is incomplete, and one promise depends on it.**
  README:1075: `umbral.db` holds "connectors, users, apps, each app's sign-in
  logo and colour, the security log". It also holds the operator credential
  hash and the instance domain list (`settings` table), each app's sign-in
  methods, passkeys, invitations and ceremonies (`Database.fs:118-130,180-217`),
  and OpenIddict's tokens and authorizations. README:1076: `keys/` holds
  `signing.pfx`, `encryption.pfx` (`Infrastructure/Keys.fs:34-38`) and the Data
  Protection key ring, which also protects the admin and session cookies and
  the antiforgery tokens (`Program.fs:131-140`). So README:1066 ("people stay
  signed in") holds only when `keys/` comes back, and a restore brings back the
  operator credential and everyone's passkeys, which the section never says.
- **W13. README:1299** says the specification is in `specs/001-umbral-mvp/`.
  There are nine specs (001 to 009); say `specs/`, one folder per feature.
- **W14. Memory figures.** README:60-61, :67 and PRODUCT.md say "under 150 MB";
  the tests assert 150 MiB and 160 MiB on Ubuntu 24.04 runners
  (`tests/Umbral.Tests/IdleMemoryTests.fs:73-81`, `ci.yml:28-33`). "Raspberry Pi
  4 or 5" (README:66) is a reasonable claim no test backs. Nit.

### Secret-store walkthroughs

- **W19. All four say the cache rides out a refused credential.** The
  troubleshooting row for the startup warning (`aws.md:184`, `azure.md:179`,
  `gcp.md:192`, `bellabaxter.md:159`) ends "Sign-ins keep working from the cache

- **W21. `aws.md:65-66`** says "Settings for the prefix and the cache are in the

- **W22. The shared paragraphs have drifted.** "The cache and the grace period"

## 2. Missing

### The zero-to-login path (Principle VI)

- **M1. Quick start step 5 never says to click Create app.** README:220: "Open

  build needs Docker BuildKit (`--mount=type=cache`, `$BUILDPLATFORM` in the
  Dockerfile) and downloads the Tailwind CLI from github.com
  (`Assets/build-css.sh:61`); README:99 mentions only the .NET SDK.
- **M3. Quick start step 3.** The form has a **Confirm credential** field and

  `docker logs umbral` straight after `docker run -d` can run before the banner
  is printed; say "give it a few seconds".

### README sections

- **M4. "Integrate an app" leaves out what an app developer needs next.**
  - The endpoints: `/connect/authorize`, `/connect/token`, `/connect/userinfo`
    (GET and POST), `/connect/logout`, `/connect/revoke`
    (`OpenIddictSetup.fs:33-47,282-287`). Introspection is registered but apps
    are not permitted to call it (`Infrastructure/AppClients.fs:16-25`).
  - Logout: `/connect/logout` ends Umbral's session only, never the provider's,
    and accepts only the registered post-logout URI
    (`Handlers/Connect/EndSession.fs`).
  - Email is first-seen: `COALESCE(email, @email)` (`UserStore.fs:154`), so a
    changed email at the provider never changes the `email` claim; only
    `email_verified` can go from false to true.
  - Linking edge cases: the existing user's stored email must itself be
    verified, and when two users match, Umbral creates a third rather than
    guess (`Domains/Linking.fs`, `AmbiguousMatch`).
  - `email`, `name` and `picture` are in the id_token only when the scope was
    requested (`Authorize.fs:38-70`).
  - What a disabled person sees ("This account has been disabled. Contact
    whoever runs this Umbral.", `Texts.fs:596`), and that deleting a user
    revokes their tokens too (`Handlers/Admin/UserDelete.fs`).
- **M5. "Who can sign in".** Domains are stored as IDN ASCII and shown back in
  Unicode (`Domains/EmailDomains.fs`); a single-label name or an IP is refused
  as "not a domain"; a Google connector with a rule sends Google an `hd` hint
  (`Handlers/Connect/Start.fs:86-99`), which is only a hint. The section never
  mentions disabling a user, the other way to turn someone away; link to it.
- **M6. Passkeys.** The invitation link is `<origin>/invite/<secret>`
  (`Domains/Passkeys.fs`); the note is limited to 64 characters (`Texts.fs:699`);
  the home page's **Your passkeys** link shows whenever a passkey connector row
  exists, enabled or not (`Handlers/Home.fs:40-42`), and the page then says
  "Passkeys are not enabled on this Umbral"; finished invitations are pruned
  after 30 days (`Infrastructure/PasskeyInvitations.fs`).
- **M7. "Run it for real".** Quote the origin-mismatch banner
  (`Texts.fs:901-904`: "Umbral is configured with the public address …, but you
  reached it at …") so a reader can search for it. Traefik is named but not
  covered: it forwards `X-Forwarded-For`, `-Proto` and `-Host` by default.
  Nothing sets the forwarded-header limit, so only the last proxy hop is read
  (ASP.NET's default of 1): a CDN in front of the proxy reports the CDN's
  address. (Not verified at run time; verify before writing it.)
- **M8. Backup.** Name `UMBRAL__DATA_DIRECTORY` as the setting that moves
  `/data`; say that passkeys and the operator credential are in the backup
  (W12).
- **M9. Settings and troubleshooting.** `ASPNETCORE_HTTP_PORTS` (default 8080
  from the base image; the health check follows it, `Program.fs:605-610`) is
  not in the table. `UMBRAL__ALLOW_FAKE_CONNECTOR` (`Providers/Fake.fs:40-49`,
  development only) is nowhere; say in Contributing that it exists and is
  dev-only, or leave it out on purpose. The "container exits" entry
  (README:1205) lists three causes; the code also refuses to start on a bad
  `UMBRAL__SECRET_STORE*` or `UMBRAL__AZURE_KEY_VAULT_URI` value, a missing
  `AWS_REGION` or `GOOGLE_CLOUD_PROJECT`, or a missing Bella Baxter credential
  (`Texts.fs:722-748`), and each message names the variable.
- **M10. Troubleshooting entries that do not exist yet:** "Passkeys are not
  enabled on this Umbral" (what it means, and that the home link shows anyway);
  a false origin-mismatch banner behind nginx (W9).
- **M11. `move-secrets`.** The passkey connector prints `skipped … has no secret
  to move` and counts as in place (`SecretMove.fs`, `Texts.fs:1075`); `--dry-run`
  contacts no store.

### Connector and store walkthroughs

- **M12. The connector card itself.** Discord, GitHub and Google's step 3
  describes only Client ID, Client secret and Save. The card also has an
  editable **Button label** (default: the provider's name), the **Shared with

  endpoint 5xx shows as "provider unreachable" and a 4xx as "Sign-in didn't
  complete" (`Oidc.fs`, `exchangeCode`).
- **M17. Passkey: three rules.** User verification and a resident key are both
  required (`WebAuthn.fs:128-129,150`), so a security key with no PIN or
  biometric is refused (`user_verification_missing`); a ceremony expires after
  5 minutes (`Domains/Passkeys.fs:29`); the card has Enable, Disable and Delete
  (`Handlers/Admin/PasskeyConnector.fs:170-195`), and deleting the connector
  removes its invitations but not anyone's passkeys.
- **M18. Stores: four shared omissions.** `UMBRAL__SECRET_CACHE_SECONDS=0`
  turns the cache off (`Registry.fs:257`); the `warning` line's meaning (the
  move happened, the old copy could not be deleted, remove it by hand,
  `Texts.fs:1058-1063`), the dry-run `would move` line and the passkey
  `skipped` line; which variables must stay set to move *out* of a store
  (`Infrastructure/SecretStores/Wiring.fs`, `readerVariables`: for AWS one of
  `AWS_REGION`, `AWS_ACCESS_KEY_ID`, `AWS_PROFILE`, `AWS_WEB_IDENTITY_TOKEN_FILE`;
  for Azure `AZURE_CLIENT_ID`, `AZURE_TENANT_ID` or the vault URI; for GCP
  `GOOGLE_APPLICATION_CREDENTIALS` or `GOOGLE_CLOUD_PROJECT`); and the
  "bad setting stops the start, unreachable store starts with a warning"
  sentence that only `aws.md` has.
- **M19. Bella Baxter: what the key must be allowed to do.** The adapter lists
  providers and creates, updates, reads and deletes secrets
  (`SecretStores/BellaBaxter.fs:300,360,408-417`); the doc never says so. GCP:
  secrets are created with automatic replication (`Gcp.fs:262`), which an org
  policy can forbid.
- **M20. "What the provider learns".** No connector walkthrough says what the
  provider sees: Umbral's server-side callback, the application name the
  operator chose, and nothing about which app the person is signing in to. The
  passkey walkthrough's "What Umbral stores" is the model. Spec 010's

## 3. Error messages without a next action (Principle VI)

Counted: about 150 distinct failure messages in `Views/Texts.fs` plus the
handlers. About 125 are operator-facing; 8 of those state no next action and 9
state a partial one. Every `noticeEn` code except the ones below says what to
do. The startup refusals (`PublicOrigin`, `DataDirectory`, `TrustedProxies`,
`Database.fs:380-386`, the secret-store settings at `Texts.fs:722-748`) are all
good: the variable's name and what to set it to.

**Wrong message, not just a missing action**

- **E1.** `Handlers/Admin/Credential.fs:100`: when the credential was changed in
  another session (`AdminAuth.AlreadyConfigured`), the operator is sent to the
  `setup-too-short` notice, "Use at least 12 characters, then submit the form
  again" (`Texts.fs:589`), which is false. Add a code: "The credential was
  changed in another session. Sign in again with the new one."

**Operator-facing, no next action**

- **E2.** `Texts.fs:1103` `PasskeysNotEnabled`: "Passkeys are not enabled on
  this Umbral." Shown on `/account/passkeys`, to operators and people alike.
  Add: "Ask whoever runs this Umbral to enable them, or sign in another way."
- **E3.** `Texts.fs:1066` `MoveMismatch`: "{store} did not return what was
  written to it". Add: "Check the store's permissions and any replication or
  versioning on it, then run move-secrets again; the connector still uses its
  old copy." `Texts.fs:1057` (`MoveFailed` tail) likewise: "Fix the cause
  above, then run move-secrets again."
- **E4.** `Handlers/Health.fs:29-31`: "Health check could not reach the
  database". Add what to check: the data directory volume is mounted and
  writable, `docker logs umbral`.
- **E5.** `Program.fs:568`: "The credential could not be replaced: {why}". Add:
  "Check that the data directory is mounted at the same path as in the running
  container, then run it again."
- **E6.** `Program.fs:428`: "The startup check of the secret store failed with
  {Exception}." Add that this is a bug in the store adapter, to report with the
  exception type.
- **E7.** `Infrastructure/ConnectorStore.fs:31`: "The connector '{slug}' has an
  unknown kind '{kind}'." Add: "This image is older than the database, or the
  row was edited by hand: run the newer image, or restore the backup."
- **E8.** `Handlers/Connect/Authorize.fs:197`, `EndSession.fs:21`,
  `Token.fs:32`: wiring failures ("route and endpoint URI disagree") surface as

## 6. The documentation review process

The maintainer proposed mirroring the design review. Confirmed, with the
details below.

**Who.** The reviewer is the `umbral-documentation` Claude Code session
(address "umbral-documentation [f9c565]" if the bare name is ambiguous).
Implementers that run as Claude Code sessions message it directly; the
maintainer relays otherwise.

**What the implementer sends.** The branch, the commit range, and the list of
doc files touched. On the branch, `.alta/reviews/<task>/notes.md` with:

- the doc files changed and, for each statement that describes behaviour, the
  code it was checked against (file and line), or "quoted from Texts.fs";
- for a walkthrough, confirmation that the required sections are present, in
  this order: what it is; Before you start; the numbered setup steps (where to
  create the app, the redirect URI to paste, the credentials into Umbral);
  Giving one app its own name (where it applies); Scopes Umbral requests; What
  people see; What Umbral takes from the provider; What the provider learns;
  Allowed email domains (or why they do not apply); Troubleshooting; Gotchas;
- how it was verified (a walk through the steps, a test run, the link check);
- the CHANGELOG entry, if the change is one people who run Umbral notice.

No captures are needed for a doc review, unless the doc quotes or describes a
screen that changed in the same task; then the design review's captures serve
both.

**What the reviewer does.** Reads the diff against the code, not against the
description. Writes `.alta/reviews/<task>/review.md` on the branch, each
finding marked **blocking** or **nit**:

- blocking: a statement the code contradicts; a quoted UI string that is not
  in `Texts.fs` verbatim; a Principle VI gap (a step a reader cannot complete
  from the page, an operator-facing error with no next action, a connector
  without its walkthrough); a dead link or anchor; a CHANGELOG entry missing or
  under a released section; a permission or setting the code does not use;
- nit: wording, order, length, a missing cross-link, a sentence that is right
  but will not survive the next change.

**Then.** One re-check after the implementer answers in `notes.md`, and no
merge until `review.md` says clear. The maintainer merges.

**What the reviewer does not do.** Rewrite the text itself (it proposes wording
in the finding), judge the design of a screen (that is `umbral-designer`), or
merge.
